# Анализ проекта «Синий флаг»: расширяемость и поддержка

Анализировался код из `bingoLectures.zip`: Express 4 + EJS + PostgreSQL, `server.js` (~440 строк), `db.js`, 8 шаблонов, один `style.css`.

## 1. Что в проекте уже сделано хорошо (и сохранено)

- Весь SQL параметризован; CSRF-токен на всех изменяющих запросах; bcrypt с «пустым» хешем для выравнивания времени ответа; `session.regenerate` при входе.
- Транзакции там, где нужна атомарность (сохранение карточки, результаты, импорт).
- Ключевое свойство игры соблюдено на сервере: пока приём карточек открыт, результаты и очки вообще не попадают в ответ. Рулетка тоже решается на сервере и не перекручивается.
- Разумные ограничения длины полей и размера импорта.

## 2. Найденные проблемы и что с ними сделано

| # | Проблема | Чем грозит | Что сделано при переносе |
|---|---|---|---|
| 1 | `server.js` — монолит: роуты, SQL, правила игры, валидация, рендер в одном файле | Каждая правка рискованна, тесты невозможны | Слои `routes → services → repositories`, SQL только в репозиториях |
| 2 | Правила продублированы: очки 1/3/5/10 — в `server.js`, в `CHECK` базы, в текстах ошибок и шаблонах (`=== 10`, «8 или 9» слотов) | Добавить уровень очков = править 5 мест и писать миграцию | Один файл `domain/rules.js`; клиент получает правила из `/api/me`; `CHECK` по набору очков убран |
| 3 | Формула очков скопирована в два больших SQL (событие и общий рейтинг) | Расхождение рейтингов при правке одного из них | View `card_scores` (миграция 003) — единственное определение |
| 4 | Схема создавалась `CREATE IF NOT EXISTS` + блок `MIGRATE`, который на каждом старте делал `DROP/ADD CONSTRAINT` | Нельзя безопасно менять схему, нет истории изменений | Раннер миграций (`schema_migrations`, advisory lock), SQL-файлы по порядку |
| 5 | Нет индексов под реальные запросы (`event_id`, `(event_id, user_id)`); PK их не покрывает | Деградация при росте числа карточек | Миграция 002 |
| 6 | Циклы `UPDATE`/`INSERT` по одной записи (результаты, карточка, импорт) | Много round-trip’ов к БД | Пакетные запросы через `unnest` |
| 7 | Статус события переключался «тумблером»: двойной клик или повтор запроса возвращал прежнее состояние | Событие случайно закрывается/открывается, результаты то скрыты, то видны | Явный `PUT /status {status}` — идемпотентно |
| 8 | `SESSION_SECRET` с запасным `'dev-secret'`; cookie без `secure`; нет `trust proxy`, `helmet`, ограничения попыток входа | Подделка сессий при забытой переменной, перебор паролей | В production секрет обязателен, `secure: 'auto'`, `helmet` + CSP, rate-limit на вход/регистрацию, сравнение CSRF через `timingSafeEqual` |
| 9 | Flash-сообщения в сессии и подмена `res.redirect` ради гонки сохранения | Хрупкий код, лишние записи сессии в БД | В SPA не нужны: тосты на клиенте |
| 10 | CSS вставлялся в `<head>` каждого ответа; в dev читался с диска на каждый запрос | Лишний трафик, нет кэширования | Сборка Vite с хешированными файлами и кэшем |
| 11 | Нет тестов, проверки зависят от ручного прохода | Регрессии при любом рефакторинге | 6 юнит-тестов домена + сквозной `smoke`-скрипт API |
| 12 | Прямое чтение `process.env` в нескольких местах | Ошибки конфигурации видны поздно | `config.js` с проверкой при старте; `/api/health` |

## 3. Что остаётся (не делалось — решайте по необходимости)

**Целостность данных (стоит сделать первым)**
- `card_picks.event_id` дублирует событие пика, но БД не проверяет, что они совпадают. Лечится составным внешним ключом `(pick_id, event_id) → picks(id, event_id)`. Не добавлено, чтобы не рисковать на уже существующих данных без их проверки.
- Удаление пика или человека, который уже в чьей-то карточке, молча меняет карточки игроков. Варианты: запретить удаление после первой карточки или помечать удалённым.
- Требование «ровно 8/9 пиков в карточке» проверяется только в коде; если админ удалит пики после сбора карточек, у игроков окажутся неполные карточки.

**Расширяемость игры**
- «Пик на человека» — частный случай, зашитый в схему (`people`, `card_person`) и в код. Если планируются другие особые ячейки, обобщите до таблицы «слотов» с типом (`regular`, `person`, …) и стратегиями подсчёта очков.
- Права: сейчас только `user`/`admin`. Для нескольких организаторов понадобится связь `event_admins`.

**Клиент**
- При росте числа страниц заменить `useApi` на TanStack Query (кэш, оптимистичные обновления) — интерфейс хука совместим.
- Вынести админку в отдельный чанк (`React.lazy`), сейчас весь клиент ≈ 62 КБ gzip, это не критично.
- Тесты компонентов (Vitest + Testing Library). Сценарии «регистрация → рулетка → карточка» и «админка» я прогонял одноразово в jsdom против живого сервера, в репозиторий они не включены, так как требуют запущенной БД.
- Единый CSS можно со временем разнести по компонентам (CSS Modules); сейчас сохранён без изменений, чтобы внешний вид не менялся.

**Инфраструктура**
- CI (установка, `npm test`, `npm run build`), ESLint/Prettier, Dockerfile.
- Структурные логи (pino) с id запроса, мониторинг ошибок, резервные копии БД.
- Нативная зависимость `bcrypt` иногда мешает деплою на платформах без сборки; запасные варианты — `bcryptjs` или `argon2`.
- Валидация входных данных схемами (zod) вместо ручных проверок; при желании — TypeScript.
- Сброс пароля, журнал действий администратора.

**Производительность**
- Общий рейтинг считается «на лету» по view. Для сотен игроков это быстро; при тысячах — материализованное представление или кэш и пагинация.

## 4. Что проверено при переносе

Выполнено и пройдено: сквозная проверка API (вход, импорт, рулетка, невозможность перекрутки, валидация карточки, скрытие результатов пока приём открыт, подсчёт очков после закрытия, права админа, экспорт); юнит-тесты; два UI-сценария в jsdom на реальном бэкенде; продакшн-сборка клиента и раздача SPA через Express; запуск миграций поверх базы, созданной старым кодом (очки совпали, повторный запуск ничего не меняет).

**Не проверено:** внешний вид в реальном браузере (особенно iOS Safari, где раньше были проблемы с внешним CSS) и загрузка веб-шрифтов — в среде не было браузера. Перед выкладкой пройдите по основным экранам на телефоне. Также не проверялся ваш реальный деплой (платформа, прокси, HTTPS).
